## 项目介绍

**Lumina Walk（寻光漫游）** 是一个面向摄影爱好者的地点发现与交流平台。用户可以浏览拍摄地点、发布摄影笔记、关注创作者，也可以领取抢购优惠券，并通过 AI 助手查询地点信息、整理拍摄建议和规划行程。

项目以“黑马点评”的业务代码为基础进行二次开发。我保留了登录、地点查询、笔记互动、优惠券和订单等基础链路，重点围绕**高并发交易**与**AI 应用落地**做了扩展。相比单独做一个聊天页面，我更希望让 AI 助手接入平台已有的地点、笔记和业务规则，能够回答与用户当前任务有关的问题。

### 我重点改造的部分

**后端业务链路：**

- 在地点详情查询中结合布隆过滤器与空值缓存，减少无效 ID 请求对数据库的冲击。
- 基于注解、AOP、Redis ZSet 和 Lua 实现滑动窗口限流，为普通接口、秒杀入口和 AI 请求配置不同的访问额度。
- 将秒杀链路拆为 Redis Lua 资格校验、RocketMQ 异步创建订单和数据库库存扣减，处理一人一单、库存竞争及消息重复消费。
- 通过 RocketMQ 延迟消息触发未支付订单的超时检查，围绕支付回调与关单设计订单状态判断和并发处理。

**AI 应用链路：**

- 基于 Spring AI 实现手动控制的 Think–Execute 循环：模型决定下一步需要什么信息，服务端负责工具注册、执行、日志记录、步数控制和任务退出。
- 使用 Milvus 分别构建**平台知识、地点画像、摄影笔记**三类索引。平台规则结合向量召回与关键词补召回，地点推荐和笔记分析则侧重语义检索。
- 持久化会话、消息和工具记录；每轮推理只加载最近的对话窗口，在支持连续追问的同时控制输入上下文的长度。
- 将消息提交与 Agent 执行解耦，通过 SSE 推送执行状态、工具结果和回答片段；连接中断后，前端还可以通过已保存的消息恢复回答。
- 为路线、天气等外部信息预留工具接入方式，并提供本地兜底，使 Agent 可以在外部工具不可用时完成可用的基础回复。

### 用户可以完成什么

1. **登录并浏览摄影内容：**使用验证码登录后，浏览地点分类、摄影笔记热榜和地点详情；提供坐标时，还可以查询附近地点。
2. **发布与互动：**发布摄影笔记，对笔记点赞，关注创作者，并在关注流中查看他们的新内容。
3. **领券与查看订单：**购买普通券或参与秒杀抢券。秒杀请求先返回订单受理结果，随后可查询订单状态，并观察支付与超时关单过程。
4. **使用摄影助手：**提出地点推荐、单地点分析、拍摄攻略、路线与天气相关问题。查看 Agent 的处理进度，并基于历史会话继续追问。

接下来重点记录了我在二开中遇到的具体问题，以及从缓存、异步订单到 RAG、Agent 和流式交互的设计与取舍。

1. 缓存穿透问题：布隆过滤器+空值缓存
   地点和券的详情查询是一个高频查询接口。正常情况下，大部分请求都会命中已有地点。但如果有人不断请求不存在的 ID，Redis 查不到数据，请求就会继续打到 MySQL。由于这些 ID 本来就不存在，数据库查完也无法生成正常缓存，下一次请求仍会重复查库。这就是缓存穿透问题。
   我先比较了两种处理方式：
   - **缓存空值：**数据库确认 ID 不存在后，在 Redis 中写入一个短期空值。相同 ID 再次请求时直接返回，不再查库。这种实现虽然简单，但是其实每个新出现的无效 ID 依然会先访问一次数据库。
   - **布隆过滤器：**在查缓存之前，先判断 ID 是否可能存在。明确不存在的 ID 可以直接拦截，连 Redis 中的详情缓存和数据库都不必访问。它适合挡住大量分散的无效 ID。但存在误判：某个不存在的 ID 也可能被判断为“可能存在”。
   所以最好的选择是让两者处理不同阶段的问题。请求先经过布隆过滤器，过滤掉绝大多数不存在的 ID。少量误判而放行的请求，如果查库后仍不存在，再写入短期空值。这样，布隆过滤器负责拦截大量分散请求，空值缓存负责拦截同一个无效 ID 的重复请求。
   
   最终方案：针对高频查询接口采用“布隆过滤器 → Redis 详情缓存 → MySQL 回查 → 空值缓存”的处理。实现中的一个关键点是新增地点后还要同步更新布隆过滤器：否则数据库里已经有新地点，过滤器却仍判断它不存在，正常请求会在入口被拦掉。

2. 缓存击穿问题：热点数据过期时，优先保证新数据还是请求响应？
   缓存穿透处理的是“不存在的数据”。缓存击穿处理的是确实存在、而且访问量很高的数据。假如一个热门摄影地点的详情缓存刚好过期，大量请求同时发现缓存未命中，接着一起查数据库、重建同一个 Key，数据库会在短时间内承受集中压力。
   针对这个问题，可能的解决方案如下：
   - **互斥锁重建：**缓存失效后，请求竞争同一把锁，只有拿到锁的线程查库并重建缓存，其他请求等待后重试。这样能避免大量线程同时查库，而且等待的请求最终可以读到重建后的数据。代价是热点 Key 过期时，一部分请求的响应时间会变长。
   - **逻辑过期：**Key 不因物理 TTL 到期而立即消失，而是在缓存内容中记录逻辑过期时间。读请求发现数据过期后，尝试由一个线程在后台重建，当前请求先返回旧数据。它能让热点请求继续得到响应，但需要接受一段时间内读取旧值，并提前准备好初始缓存。
   
   这两种方案方案的权衡，关键是看这份数据能不能短暂使用旧版本。 在该项目中，摄影地点的介绍、图片等展示信息，可以考虑逻辑过期。用户对几秒钟的延迟并不敏感，更重要的是系统在高峰期依然稳定可用。 库存、订单状态这类会影响交易判断的数据，则不适合用“先返回旧值”的思路。
   **最终方案：**将互斥锁和逻辑过期都封装在缓存组件中，作为热点数据的两种重建策略。当前地点详情接口实际使用的是普通 TTL 与空值缓存。如果后续某些地点形成稳定热点，会先预热这些 Key，再将适合短暂返回旧数据的展示字段切换到逻辑过期。这样选择策略的依据是数据的一致性要求，而不是给所有接口套同一种缓存方案。

3. 缓存雪崩问题
   如果大量缓存 Key 在相近时间失效，请求就可能同时回到数据库。单个 Key 失效可以通过互斥重建处理。但当失效的是一批不同的 Key 时，即使每个 Key 只由一个请求重建，数据库仍可能承受一波集中的查询。这就是缓存雪崩更难处理的地方。
   因此，缓存雪崩需要控制的是失效时间和回源速度。
   对此问题，我在该项目的处理思路分成三层：
   - **第一层，打散过期时间。** 批量写入缓存时，不让所有 Key 使用完全相同的过期时刻，而是在基础 TTL 上增加随机偏移。它解决的是“本来可以分散处理的回源，却因为同时过期而挤到一起”的问题。
   - **第二层，按数据特点选择缓存策略。** 普通地点详情可以设置物理 TTL，让数据定期回源更新。少量访问特别集中的展示数据，可以考虑预热后使用逻辑过期，把重建放到后台。
   - **第三层，在入口限制回源速度。** 缓存层无法保证永远可用，因此请求到达业务逻辑前还需要限流。项目中的限流采用注解、AOP、Redis ZSet 和 Lua：按配置统计最近时间窗口内的请求，并原子完成判断与记录。缓存异常或集中失效时，限流至少能约束进入后端的请求量，避免压力毫无控制地传给数据库。
   - 同时，数据库本身也要做好连接池和慢查询防护。


4. 消息队列的选择————RocketMQ
   秒杀请求的流量会在开售瞬间集中到达。如果每个请求都同步完成订单落库，数据库会直接承受这一波写入压力。因此，我把“判断用户是否抢到资格”和“创建数据库订单”拆开：前者在请求链路中快速完成，后者交给消息队列异步处理。
   但这个场景对消息队列还有第二个要求：**订单创建后，如果用户在规定时间内没有支付，需要触发超时关单。**所以选型时，不仅只是关注吞吐量，而是要看两个业务动作能否自然地串起来：异步创建订单，以及在指定时间后检查订单状态。
   可能的解决方案如下：
   - **Kafka：** 擅长处理大规模事件流、日志和数据管道。用它承接秒杀下单消息没问题，但超时关单通常还需要额外设计定时调度或延迟处理机制。对于当前订单链路，吞吐能力不是唯一决定因素。
   - **RabbitMQ：** 路由方式灵活，也能通过 TTL 与死信交换机，或相应的延迟机制实现超时检查。它完全可以完成这项工作，只是订单创建和延迟关单需要组合更多队列与路由配置。
   - **RocketMQ：** 既能承接异步下单消息，也直接提供延迟消息能力。订单创建消息交给消费者落库，超时消息到期后再读取订单状态：已支付就结束，仍未支付才执行关单。两类消息围绕同一笔订单展开，链路比较直观。
   ** 所以真正的难点不在于把消息发出去，而在于处理消息到达后的不确定性。**消费者可能重复收到创建消息，超时检查也可能与支付操作接近同时发生。因此订单 ID、消费幂等和订单状态判断必须贯穿两条消息链路；延迟消息负责“到时间发起检查”，不能单凭收到消息就认定了订单应该关闭。
   ** 最终方案：**RocketMQ。能用比较直接的方式表达这条业务流程：抢购资格确认 → 异步创建订单 → 延迟检查支付状态 → 超时关单。选型的核心是订单生命周期与消息能力的匹配，而不是简单比较三种 MQ 谁的吞吐量最高。

   5. 为什么选择滑动窗口限流？ 
   项目早期的接口主要是普通查询和交易请求。接入 AI 助手后，一次请求可能继续触发多轮模型推理、知识检索、工具调用和 SSE 推送。不同接口消耗的资源差别很大，如果等请求进入业务逻辑后才处理突发流量，数据库、线程池或模型服务可能已经承受了压力。因此我希望把限流放在入口，并根据接口成本设置不同额度。
   我比较了几种常见算法：
   - **固定窗口：** 按分钟或秒计数，实现简单。但请求可以集中在前一个窗口的末尾和后一个窗口的开头，使很短时间内通过的请求数超过预期。
   - **漏桶：** 以相对固定的速率处理请求，适合希望输出速率平稳的场景。但秒杀开售时，请求天然集中；如果系统能够承接一定突发量，始终匀速放行未必是最合适的选择。
   - **令牌桶：** 持续生成令牌，允许在桶容量范围内处理短时突发。如果目标是既控制长期平均速率，又允许一波明确的流量峰值，它是很好的方案。但桶容量越大，瞬间允许通过的请求也越多，需要额外判断下游能否承受这个峰值。
   - **滑动窗口：** 统计“当前时刻往前一段时间”内已经通过的请求。相比固定窗口，它不会因为整点切换而重置计数；相比允许积累突发额度的令牌桶，它更适合表达“任意连续一分钟内，每个用户最多发起 N 次 AI 请求”这样的规则。

   - 这里最关键的取舍是：**想限制的是平均处理速率，还是任意连续时间段内的请求次数？** 对 AI 对话和秒杀入口，我更关心后者。前者一次请求成本高，需要控制用户连续发问；后者流量集中，需要避免窗口交界处突然放入过多请求。所以我选择滑动窗口作为这类接口的统一限流规则，再为不同接口配置不同阈值。
   实现上，Redis ZSet 用时间戳记录窗口内的请求，先移除过期记录，再统计当前窗口数量。判断是否超限与记录本次请求必须在一次 Lua 执行中完成；否则两个并发请求可能同时看到“还差一个名额”，最后都被放行。注解负责声明接口的限流规则，AOP 负责在业务方法执行前拦截，Lua 负责保证计数与写入的原子性。
   **最终方案：** 选择滑动窗口并不是因为它在所有场景下都优于令牌桶。而是因为它最贴合项目当前要表达的规则：**限制任意连续时间段内的请求密度，并按业务接口区分资源成本。** 这样设计把限流从某个秒杀接口的局部优化，变成了交易与 AI 请求都能使用的入口治理能力。

6. 秒杀链路：从防超卖，到异步下单
   秒杀最先要解决的不是“怎样插入一条订单”，而是开售瞬间大量请求到来时，怎样快速判断还有没有库存、这个用户是否已经抢过，同时避免所有请求都进入数据库。我沿着这两个约束，逐步调整了方案。
   - 第一版，直接查库存再扣减。这很容易写，但“查询库存大于 0”和“扣减库存”是两个动作。库存只剩 1 时，请求 A、B 都可能先读到 1，再分别执行扣减。问题的根源不是代码执行得太慢，而是资格判断与库存扣减缺少原子性。
   - 第二版，给下单逻辑加锁。synchronized 能让单个 JVM 内的请求串行执行，但服务部署多个实例后，各实例持有的是不同的锁。于是我考虑 Redis SET NX 分布式锁，让不同实例争用同一个锁。不过，这又带来新的细节：请求 A 执行过久导致锁过期，请求 B 获取新锁后，A 不能在 finally 中直接删除这个 Key，否则会误删 B 的锁。即使给锁设置唯一标识，“先检查标识、再删除”如果分成两次 Redis 操作，中间仍可能发生锁过期和重新获取。
   到这里我发现：**为一次库存判断让所有抢购请求排队，并不是最合适的方向。** 这个场景真正需要原子执行的是“检查库存、检查一人一单、预扣库存、记录购买资格”。因此我改用 Redis Lua，把这几个动作放在一次脚本执行中。并发请求不会在“刚查完库存、还没扣减”的间隙插进来，也不必让整个订单创建过程持有一把锁。
   但 Lua 只解决了 Redis 中的资格判断。若请求还要同步等待 MySQL 完成订单落库，开售高峰仍会把响应时间和数据库写入压力绑在一起。
   - 于是继续将链路拆开：**Lua 确认资格并预扣库存 → 发送订单消息 → 返回订单 ID → 消费者异步落库。** 用户拿到订单 ID，表示抢购请求已被受理。最终订单状态由后续落库结果决定。
   同时，引入 MQ 后，难点也从“并发时怎样扣库存”扩展到了“跨组件失败时怎样收尾”：消息发送失败，需要撤回 Redis 中的库存预占与购买资格。消息重复投递，需要避免重复创建订单。数据库扣库存也仍然要带条件判断，作为最后的兜底。
   

7. 流式消息推送
   普通接口通常很快返回一个结果，但 AI 对话可能经历知识检索、多轮推理和工具调用。如果只在全部处理结束后返回一整段文字，用户在等待期间无法判断：请求是否已经收到、Agent 是否正在查询资料、还是调用已经失败。我自己在使用ai的时候也发现，这个功能不是锦上添花，而是非常必要。所以这些过程一定要变成用户能感知的状态。
   我比较了三种交互方式：
   - **轮询：** 前端定时查询任务状态，实现直接。但查询间隔短会产生大量没有新结果的请求。间隔长，状态变化又不能及时显示。
   - **WebSocket：** 支持服务端与客户端双向实时通信。如果双方需要频繁互发消息，它很合适。但当前交互是“用户提交一条问题，服务端持续返回处理状态和回答”，使用双向连接会增加连接管理成本。
   - **SSE：** 适合服务端沿一条连接持续推送事件。用户提问仍走普通 HTTP 请求，后端则把执行状态、工具结果和回答片段按事件发给前端，协议与业务流程正好对应。
   选定 SSE 后，真正的卡点不是把文字切成几段发送，而在于处理提交消息、后台执行和浏览器连接之间的时序。
   我把用户消息先持久化，事务提交后再触发异步 Agent 任务。执行过程中推送 status，生成最终回答时推送 answer_delta，完成后发送 answer_done。前端先建立订阅再提交问题，减少任务刚开始就错过事件的可能。
   连接中断也不等于任务失败：Agent 可能仍在后台运行，甚至已经把回答保存下来。因此前端在断流后根据已受理的消息查询历史结果，避免因为页面没收到最后一个事件，就再次提交同一个问题。模型流式输出失败时，后端还可以把已有候选答案分块推送，完成这次回复。
   最终方案：我选择 SSE，是因为当前业务需要的是服务端单向、持续地反馈进度和结果。它带来的价值不仅是“文字逐字出现”，更是把一次长耗时 Agent 任务拆成了已受理、处理中、工具执行、回答生成、最终完成几个可观察阶段。用户能更早看到进展，开发时也更容易定位一次对话究竟卡在哪一步。

8. RAG 检索：按知识类型分别组织
   摄影助手需要处理几类不同的问题：用户问平台规则时，希望得到明确、可靠的条款。问“周末去哪拍日落”时，需要理解拍摄偏好并找到合适地点。问某个地点值不值得去时，又需要参考与该地点关联的摄影笔记。它们都需要检索，但检索目标并不相同。
   我最初考虑过用一套向量检索处理所有内容。这样接入简单，语义相近的问题也容易召回。但在测试规则问答时，我发现一个问题：**向量相似度高，不代表一定命中了问题中的关键条款。**用户问某项会员福利或优惠券条件，知识库明明有说明，检索结果却可能被语义相近的泛化内容占据。如果直接把这些结果交给模型，后续生成再流畅，也无法弥补检索阶段漏掉的事实。
   因此，我按数据性质拆分了索引和处理方式：
   **平台知识库：** 将规则文档切成较小的片段再建立索引，避免整篇文档作为一个结果返回，让模型难以定位具体条款。
   **地点画像：** 把地址、均价这种结构化字段组织成可检索文本。这样用户可以用自然语言找地点，召回后也能看到推荐依据。
   **摄影笔记：** 将标题、地点名和正文一起构成检索文本。单独一段短笔记可能只写“傍晚侧光很好”，补上地点信息后，语义才更完整。分析指定地点时，还要先限定地点范围，避免引用其他地点的经验。
   检索策略也随之分开。地点和笔记主要依靠向量检索理解拍摄需求。平台规则则在向量召回之外加入关键词补召回（以更好找到确定性表达和专业术语），再对结果去重和排序。
   **最终方案：** 按知识类型组织 RAG，而不是让所有数据共用一条“切块、向量化、Top K、交给模型”的流水线。

9. 多轮推理：模型负责选择工具，代码负责控制执行
   用户的问题不一定能靠一次检索解决。例如“推荐一个适合周末拍人像的地点，最好离我近一些”，助手可能需要先找候选地点，再获取位置和地点资料，最后结合摄影笔记整理建议。随着问题组合增多，很难为每一种问法预先写好一条固定流程。
   我比较过两种做法：
   **固定流程：** 每个场景按预设顺序执行工具。优点是稳定、容易测试；但当用户同时提出地点、距离、笔记和路线要求时，条件分支会不断增加，流程也容易执行一些当前问题根本不需要的步骤。
   **完全交给模型执行：** 模型自行决定调用什么工具、何时结束，适应不同问法的能力更强。但如果没有明确边界，模型可能重复调用相同工具、拿到足够信息后仍继续查询，甚至在缺少必要条件时反复尝试，增加延迟和调用成本。

   固定流程适合步骤明确的任务，开放式摄影咨询则需要一定的动态决策能力。
   最后我采用手动控制的 **Think–Execute 循环**：每一轮由模型判断还缺什么信息，代码只执行已注册的工具，并把结果回填给模型进入下一轮。与此同时，代码记录每一步的状态和工具结果，限制最大执行步数，并为任务完成、工具异常、无效调用和空回答设置退出路径。
   这个设计最难的地方是决定什么时候继续，什么时候停下来。工具返回了结果，不代表问题已经解决。但继续调用工具也不一定带来新信息。因此我让模型负责判断信息是否足够，让程序负责守住工具范围和执行上限。信息足够就整理答案，缺少用户位置、地点 ID 等无法由工具补齐的条件，就提出澄清问题，而不是让 Agent 一直空转。

10. 上下文窗口管理：为什么不把全部聊天记录交给模型？
    多轮对话要理解“这家地点”“刚才推荐的第二个地方”这样的追问，就必须带上历史消息。但如果每次都把完整聊天记录送给模型，会话越长，输入 Token、调用延迟和无关信息都会持续增加。更长的上下文也不一定带来更好的回答：早期讨论过的其他地点，反而可能干扰当前问题。
    我的第一步是采用最近窗口截取。历史消息仍完整保存，但每次模型调用只加载最近一段对话。这样既能处理连续追问，又不会让单次请求的上下文随着会话长度无限增长。
    不过这里有一个需要注意的取舍：窗口越小，成本越容易控制，但用户很早之前说过的重要偏好也可能被截掉。窗口越大，信息更完整，却会引入更多噪声。所以窗口大小不是越大越好，而要根据实际问题观察：用户的追问通常跨越多少轮？哪些信息即使隔了很久仍值得保留？
    **后续优化方向：** 对于长会话，我会把“最近几轮原始消息”与“更早对话的摘要”组合使用。摘要重点保留用户明确表达的拍摄偏好、已确认的地点和仍未解决的条件。近期消息保留原文，以便正确理解指代和最新变化。摘要也需要能够更新和纠错，否则一次错误概括会在后续对话中反复影响回答。

11. 会话记忆：把“保存历史”和“送入模型”分开设计
    刚开始设计会话记忆时，我把问题理解成“聊天记录应该放 Redis 还是 MySQL”。后来发现，真正需要先区分的是两件事：用户能否找回完整历史，以及模型回答当前问题时需要读取哪些历史。它们的数据量、访问方式和生命周期都不同。
    我最终把会话分成三个层次：
    **服务端持久化历史：** 会话、用户消息、助手回答和工具记录保存下来，用于历史会话切换、问题回溯和执行过程排查。这是用户可以找回的完整记录。
    **模型工作上下文：** 每次调用只从持久化历史中选取最近窗口。它是本轮推理需要的输入，不等于完整会话，也不要求把所有工具日志重新交给模型。
    **前端当前状态：** 前端维护正在展示的消息、流式回答和执行进度，让用户在当前页面看到实时变化。页面状态负责交互体验，服务端历史负责刷新后恢复。
    这个拆分之后，Redis 的位置也更清楚了：如果以后出现大量会话并发读取、跨实例共享临时执行状态等需求，可以用它承接热点数据。但它不是“实现短期记忆”必须加入的组件。同样，向量库可以用于检索长期偏好或历史事实，但把聊天记录写成向量并不会自动让 Agent 拥有可靠的长期记忆，还需要决定哪些信息值得记、何时更新、怎样避免过期偏好影响当前回答。
    **最终方案：**我没有把会话记忆设计成单纯的存储选型，而是拆成“完整历史、当前推理上下文、页面实时状态”三个问题。这样既支持用户继续历史对话，也能独立控制每轮模型调用的 Token 成本。后续增加 Redis 热数据或向量化长期记忆时，也能明确它们各自解决什么问题。
